# 用印申请 · 合同 AI 预审接入说明

目标流程（行政确认版）：

```
员工提交「用印申请」
  → 表单里勾选「是否合同文件」+ 上传合同附件
  → 审批事件推给机器人（实例创建 / 状态变更）
  → 机器人：判定是合同 → 下载附件 → AI 预审
  → 把风险摘要写进该审批单的「评论」
  → 同时私聊当前待办审批人一张风险卡片
```

## 一、需要的三项授权（缺一不可）

| # | 在哪里 | 要开什么 | 用途 |
|---|--------|----------|------|
| 1 | 管理后台 → 审批 → 用印申请 → 更多设置 | 事件订阅：添加应用「合同预审机器人」(cli_xxxxxxxxxxxxxxxx)，勾选「审批实例创建」「审批实例状态变更」 | 审批走到机器人时收到通知 |
| 2 | 开放平台 → 事件与回调 | 添加事件「审批实例状态变更」 | SDK 订阅事件 |
| 3 | 开放平台 → 权限管理 | 应用身份：`approval:approval`、`approval:instance.comment` | 读实例详情、写审批评论 |

> 第 1 项只有公司审批管理员能做（普通账号没有管理后台权限，需联系审批管理员开通）。
> 第 3 项如为「用户身份」已有，但机器人是应用身份调用，必须开应用身份那一列。
> 若只能先给一项：优先第 1 项（没有事件，后面都跑不起来）。

## 二、拿到审批定义的 Code（approval_code）

任一方式：

1. 管理后台 → 审批 → 用印申请 → 页面地址里的 `approval_code=...`；
2. 提交一张用印申请后，机器人日志里会打印 `approval_code=xxxx`；
3. 用 `python -m src.cli approval-review <实例code>` 时也会回显。

拿到后填入 `.env`：

```
CONTRACT_APPROVAL_CODES=你的approval_code
```

留空表示「所有订阅到的审批都处理」，联调期建议先留空、上线时再收紧。

## 三、本地联调（不需要事件订阅）

拿到任意一张用印申请实例的 code（或分享链接里的 `instance_code=`）即可：

```powershell
$env:PYTHONIOENCODING="utf-8"
python -m src.cli approval-review <实例code或链接>
```

它会：读实例 → 解析表单 → 判定合同 → 下载附件 → 预审 → 生成报告 → **写审批评论**（`--no-comment` 可只审不写）。

首次联调建议先 `--no-comment`，确认表单识别对了再加评论。

## 四、事件订阅（已完成）

```powershell
python -m src.cli approval-subscribe <approval_code>
```

实测结论（2026-11-13）：**用应用身份（tenant_access_token）就能订阅**，接口是
`POST /open-apis/approval/v4/approvals/{approval_code}/subscribe`，返回 `{"code":0,"data":{},"msg":"success"}`；
重复订阅返回 `1390007 subscription existed`（视为已订阅）。

两个易混接口（踩过）：
- `POST /approval/v4/approvals/{code}/subscribe` → **应用身份**，这才是订阅审批事件用的；
- `POST /approval/v4/instances/subscription` → 需要 `subscription_type` 字段（99992402），不是这个。

订阅成功后机器人收到「审批实例状态变更」事件自动处理，`status=PENDING` 才触发。

## 五、兜底方案（没有管理员权限时）

群聊「用印预审」：把机器人拉进一个群，合同直接发群里（不用 @），机器人回风险卡片，提交人把结论贴进审批备注。零管理员权限，今天可用。

## 七、审查口径与输出格式（2026-11-13 行政要求后调整）

- **解除清单限定**：`SYSTEM_PROMPT` 不再要求模型"按这 31 项逐条体检"，改为"资深中国商事合同审查律师，自由、全面地找出所有对我不利/约定不明/无法执行/可能引发争议的条款，不要受任何固定清单限制，宁可多报不要漏报"。固定清单降级为**兜底层**（模型不可用时仍能给出基础体检结论）。
- **一条风险一行，三段式**：风险｜原文｜解释。审批评论与 md/docx 报告统一格式，例如：
  `2. [高] 付款节点与发票脱节｜原文「工程尾款 3057 元…收到乙方开具的等额发票后 7 个工作日内付清。」｜解释：尾款以收到发票为条件，但未约定乙方开票时限，乙方拖延开票即可无限期占款。`
  整条条款缺失时写「原文（合同未约定）」而不是留空。
- **条数与长度**：模型最多输出 20 条（原 30 条会导致 JSON 被 max_tokens 截断而整体降级）；`title` ≤20 字、`issue`/`suggestion` ≤60 字、`quote` 连续 8–100 字。审批评论展示 Top5（同级别优先带原文的语义风险），md 报告全量分组展示并附「修改建议」。
- **耗时与限流**：自由发散审查单份实测 45–150 秒（glm-4.7-flash），`LLM_TIMEOUT_REVIEW`（默认 180 秒）单独放宽；智谱高峰期会返回 429（1302 速率限制 / 1305 访问量过大），`src/llm.py` 对 429 单独退避 15–30 秒并重试 2 次，仍失败则降级为规则清单并在报告里注明原因。
- **必问问题**：模型基于全文提的问题排在前面（更贴合本合同），清单兜底问题排后面。

## 八、补充/变更类协议（2026-11-14 新增）

背景：一份 2 页的《技术服务协议之补充协议》被按主合同口径体检，报出 11 条"缺少主体信息/标的/规格/质量/验收/违约金/解除"的高风险——但这些条款本来就由主协议约定，协议第三条明确写着"本协议未约定的，仍由甲乙双方遵照主协议的约定执行"。误报把"综合风险"顶成了"高"，真正值钱的两条（服务范围被排除、全年预付无退款）反而被埋掉。

现在按以下四层处理：

1. **类型识别**（`src/contract/kind.py` 的 `detect_supplement`）：文件名或正文出现"补充协议/補充協議/变更协议/续签协议/延长期限/Supplement"，或正文多处出现"主协议/原协议/遵照主协议"（≥2 处），即判定为补充类协议。
2. **比例控制**：命中后，规则层不再把"清单缺失项"写进风险清单，模型层在 system prompt 后追加 `SUPPLEMENT_NOTE`，要求只审「本协议改动/新增条款本身的风险」「与主协议可能冲突的特别约定」「本协议自身可执行性（期限、含税、付款与退款、生效）」三类，缺失类提示最多 2 条且级别不高于 medium。合并阶段再把所有 `missing=true` 的模型结论剔除。
3. **综合风险只由有原文依据的风险定级**（`ReviewResult.overall`）：`高`=≥2 条带原文的高风险，`中高`=1 条，`中`=≥3 条中风险，`中低`=有中风险，`低`=无。缺失条款不再参与定级，避免"每份合同都是高"。
4. **证据否决**（`_contradicted_by_text` / `_is_noise`）：模型说"某信息缺失/未提供"，但正文里其实写了（账号有 `账号：xxx`、付款有`提前 N 个工作日支付`、有`仲裁/人民法院`、有`保密`等），直接丢弃；纯措辞/排版/括号类"风险"也丢弃。

同时新增三条确定性规则（不依赖模型）：

- **合同/服务期已届满**：`kind.find_period_end` 抽"至 YYYY 年 M 月 D 日"，早于今天即报高风险（这条救回了一个模型从没提出、但最要命的问题）。
- **预付且无退款安排**：全文有预付/提前支付、且没有任何"退款/退还/解除后结算"，报高风险（按年全额预付）或中风险。
- **对方明确不提供部分服务**：正文出现"不提供…服务/开发/实施"即报中风险，避免模型漏报（实测模型时有时无）。

效果对照（同一份扫描件）：改前 24 条（高 11、中 11、低 2，其中 15 条为误报）→ 改后 3–6 条（高 1–3、中 1–2），命中的是"期限已届满""服务被排除""预付无退款"，不再出现"缺少主体信息/标的/规格"这类假风险。测试见 `tests/test_kind.py`（13 项）。

## 十一、单轮提示词：发散 + 高危清单合并（2026-11-16）

### 为什么最终是单轮
先做过「两轮」（第一轮自由发散 + 第二轮只挑 high 收敛），实测：
- 耗时从 45 秒翻到 **112 秒**，审批人打开单子要等近两分钟才看到评论；
- 第二轮只是把第一轮的结论重排一遍，真正新增的漏报很少。

用户拍板：**改回单轮，把「自由发散」和「高危约束」写进同一份提示词**，让模型一次做完两件事。

### 提示词结构（`src/contract/llm_reviewer.py` 的 `SYSTEM_PROMPT`）
1. **第一层：自由发散**——"不要受任何固定清单限制""宁可多报，不要漏报"，先把问题全部找出来；
2. **第二层：高危收敛**——同一份提示词里给出 R1–R17 高危模式清单，要求逐条对照、命中的在 `rule` 字段填编号，
   并明确写"清单不是穷举，清单外的真高风险照样按 high 报"；
3. **定级锚点**——high 的定义与 R 清单对齐（重大损失 / 条款无效 / 无法救济）；
   并明确"不要因为是缺失就一律判 high""违约金未超 30% 不要因为偏高就判 high"；
4. **引用纪律**——`quote` 逐字连续 8–120 字、缺失条款 `quote=""` + `missing=true`、
   不推算金额比例天数、说缺失前必须先确认全文没有、`clause` 没有编号就留空。

输出仍是一份 JSON（summary / findings / questions），findings 多了 `rule` 字段（没命中就空字符串）。

### 单轮会漏的，用规则兜底（`src/contract/reviewer.py`）
实测单轮会漏掉「责任主体虚化」这类结构性风险（两轮时因为专门看一遍才抓到），所以加了第 13 条确定性规则：
正文出现「唯一（责任）承担主体」「乙方不承担施工/质量责任」这类表述 → 直接判 high。
同时补了同标题去重：规则判出的「责任主体虚化」和模型写的「责任主体虚化风险」视为同一处，只留一条。

### 实测（`out\real_contract.pdf`，监控安防工程安装合同，2026-11-16）
| 项 | 单轮（合并提示词） |
| --- | --- |
| 耗时 | **31–78 秒**（视模型是否 429 降级） |
| 结论 | 高 4 / 中 11 / 低 3 |
| 高风险命中 | 责任主体虚化（丙方实际施工人"唯一承担主体"）、付款账户代收无担保、验收异议期 7 工作日视为弃权、缺"逾期未提异议视为合格" |
| 必问 | 乙方是否对丙方质量与工期承担连带责任、总价 10057 与附件 8905 不一致 |

### 模型降级链（`src/llm.py`，与单轮/两轮无关，2026-11-16 加）
- `LLM_MODEL` 主模型 + `LLM_FALLBACK_MODELS`（逗号分隔，当前 `glm-4.5-air,glm-4-flash`）。
- 429 / 5xx / 超时 / 空内容 / JSON 不合法 → 换下一个模型；401 / key 无效 / 余额不足 → 直接失败。
- **有备用模型时 429 立即切换**，不在单模型上耗 15–45 秒退避。
- 换模型打 `log.warning("模型 %s 不可用…，改用 %s")`，日志里能看到实际用的哪个模型。
- 注意 `glm-4.7-flash` 是免费模型，白天经常整片 429（`1305 该模型当前访问量过大`），
  同时刻 `glm-4.6`/`glm-4.5-air`/`glm-4-flash` 都正常——是单模型饱和，不是账号限流。

## 十二、按「行政视角」返工：七项修复（2026-11-16）

用一个人格化的行政专员（28 岁、非法律岗、每天审 5–15 单用印申请）重看输出，**给 4 分**，
逐条核对原文后确认四个硬伤全部成立。下面每一项都是**确定性规则/后处理**，不指望模型自觉。

### 四条硬伤 → 七项修复

| # | 问题（行政的原话/原文核对） | 修复 | 位置 |
